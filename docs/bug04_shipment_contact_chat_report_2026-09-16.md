# BUG-04 Shipment Contact-to-Chat Report

تاريخ التحقق: 2026-09-16. النطاق: زر التواصل الخاص بالشحنة ونقطة get/create الموجودة، دون إنشاء نظام محادثات ثانٍ أو تعديل بيانات العملاء القائمة.

## Root Cause

الزر العربي «تواصل مع الشركة» الظاهر على بطاقة الشحنة النهائية في `TableAllShipment` كان يستدعي `_openSupport`، التي تفتح `SupportAssistancePage`. هذا هو المسار الخاطئ الذي تم التحقق منه في الكود والبطاقة التجريبية.

أما زر الدعم المرتبط بالشحنة داخل `OrderDetailPage` فكان يستخدم الشات أصلًا، لكن حماية نتيجته المتأخرة لم تكن تتحقق من تبديل جلسة الحساب. وُحّد المساران في مساعد تنقّل واحد محمي.

مشكلة باك إند مؤكدة إضافية: get/create القديم كان يعالج duplicate-key بعد `execute()` بفحص errno، لكن mysqli في وضع STRICT يرمي استثناء قبل الوصول لهذه المعالجة. لذلك طلبان متزامنان قد يمنع القيد الفريد تكرارهما، بينما يفشل أحدهما بدل إعادة المحادثة الموجودة.

## Current Button Flow Before Fix

بطاقة الشحنة النهائية → «تواصل مع الشركة» → `_openSupport` → صفحة التواصل العامة، دون رقم محادثة خاص بالشحنة.

## New Shipment Chat Flow

1. من البطاقة تُجلب تفاصيل الشحنة الحالية ويُتحقق من تطابق المعرّف الداخلي؛ من صفحة التفاصيل تُستخدم التفاصيل المعتمدة في provider الحالي.
2. يُعطّل زر الفتح ويظهر مؤشر تحميل؛ يبقى حاجز الضغط المتكرر فعالًا حتى الرجوع من المحادثة.
3. يُستدعى `ChatService.getOrCreateShipmentConversation` الموجود باستخدام `shipment_id` فقط كمعرّف مورد.
4. تُرفض النتيجة إذا تغير الحساب أو الشحنة أو غادر المستخدم موضع الفتح. تُراجع مطابقة shipment_id والنوع `shipment_client` وصلاحية conversation_id.
5. تُفتح `ConversationPage` الموجودة باستخدام conversation_id من نوع int وسياق رقم البوليصة.
6. عند الخطأ تظهر رسالة مترجمة قابلة لإعادة المحاولة ويبقى المستخدم في موضعه، دون الرجوع الصامت إلى التواصل العام.

صفحة التواصل العامة وزر المساعدة العام وFloatingChatBubble ما زالت موجودة. لم تتغير آليات الرسائل أو pagination أو optimistic send أو client_message_id أو polling أو mark-read أو روابط Firebase.

## Backend Security Verification

- action الخاص بفتح محادثة الشحنة يقبل POST فقط؛ المفتاح يُقرأ من `X-API-KEY` وليس body/query.
- هوية العميل تُشتق من جدول `tbl_clients`؛ المفتاح المفقود/غير الصالح/المكرر والحساب المعطّل مرفوضة.
- لا يعتمد مسار Flutter على `client_id` أو `sender_id` أو `store_id` أو `recipient_id` للتفويض.
- التحقق من `tbl_shipments.store_id` مقابل العميل المصادق عليه يحدث داخل transaction مع قفل صف الشحنة حتى اكتمال get/create.
- نوع المحادثة محدد على السيرفر بـ`shipment_client`؛ التحقق من القراءة يرفض نوع السائق حتى مع participant مزور في الاختبار.
- الملكية تُفحص حتى للمحادثة الموجودة؛ صاحب الشحنة السابق لا يمكنه إعادة فتح/قراءة محادثتها بعد تغيير مالكها في الاختبار.
- 401 لرفض المصادقة، 403 لعدم الملكية، 404 لغياب الشحنة، ورسالة 500 عامة لاستثناءات الخدمة. مسار عدم توفر قاعدة البيانات العام 503 لم يتغير.
- الاستعلامات prepared statements وعددها ثابت، دون حلقة N+1.
- نُقلت تهيئة الخدمة والمصادقة داخل try/catch الحالي؛ لا SQL ولا stack trace في الاستجابة العامة.

اختبارات الأمان أدناه تشغّل كلاس الخدمة الحقيقي على قاعدة معزولة. تعيين HTTP statuses وطريقة الطلب ومصدر المفتاح تحققت بمراجعة endpoint؛ ليست هذه دعوى تنفيذ اختبارات HTTP هجومية على السيرفر الرئيسي.

## Duplicate Conversation Protection

تم الاحتفاظ بالقيد الموجود `uniq_chat_shipment_client (conversation_type, shipment_id, client_id)` واستخدام `INSERT ... ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id)` للحصول على نفس المعرّف ذريًا، حتى في STRICT mode. participant creation داخل نفس transaction، وتفشله يؤدي إلى rollback.

اختباران من عمليتي PHP مستقلتين بدأا أثناء حجز صف الشحنة، ثم عادا بنفس رقم المحادثة؛ أبلغ واحد فقط عن الإنشاء، وعدد الصفوف النهائي كان واحدًا. تكرار الفتح خمس مرات أعاد نفس المعرّف دون إضافة مشاركين مكررين.

لا migration جديدة. يلزم بقاء القيود الأصلية وجداول InnoDB في بيئة السيرفر؛ تم إثباتها في migration المحلية وقاعدة الاختبار، ولم يتم فحص schema الرئيسي مباشرة.

## Account Isolation Protection

`ShipmentChatNavigation` يرث `UserScopedNotifier` الموجود، وبالتالي يتبع `UserSessionState`. تُلتقط generation للعملية وتُراجع بعد الانتظار وقبل التنقل. logout/accountChanged/dispose أو تغيير الشحنة يبطل النتيجة المتأخرة. operation token يمنع finally لعملية قديمة من مسح حالة عملية جديدة.

الاختبارات تشمل A → logout، وA → B مع اكتمال طلب A بعد بدء B، وتغيير الشحنة على نفس Widget State. لا يمكن لهذه النتائج فتح محادثة A داخل حساب B.
